# ERC-165 Interface Detection

> **ERC-165 lets a contract declare support for an interface ID through a standard read call. It is a capability claim, not a behavioral proof.**

## Interface IDs

For a Solidity interface, take the four-byte selector of each function and XOR them together:

```text
interfaceId = selectorA XOR selectorB XOR selectorC ...
```

A contract implements:

```solidity
supportsInterface(bytes4 interfaceId) returns (bool)
```

Callers can ask whether it claims support for ERC-721, ERC-1155, receiver callbacks, or another ERC-165-defined interface.

## Why detection helps

Without a standard query, a caller might try a function and interpret any revert, empty return, or fallback behavior. ERC-165 provides a cheap, explicit compatibility check before interaction.

NFT standards use it to expose their main and optional interfaces.

## What it cannot guarantee

A malicious contract can return `true` for every ID and then behave incorrectly. A buggy contract can implement functions but report `false`. Proxy upgrades can change behavior after a previous check.

```text
supportsInterface = declared capability
correct execution = separate trust and testing question
```

ERC-165 detects function-set intention, not semantics, safety, authorization, or economic behavior.

## Interface ID is not a contract fingerprint

The ID is only four bytes and built from selectors. It does not uniquely identify source code or implementation version.

Different contracts should share an interface ID when they expose the same standard API. That is the purpose.

Callers should also limit gas for detection as specified, handle reverts, and avoid assuming every historical contract implements ERC-165 even if it behaves like a familiar token.

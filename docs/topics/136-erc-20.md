# ERC-20

> **ERC-20 standardizes the interface for fungible token balances and delegated transfers; it does not standardize token economics or trust.**

## Fungible accounting

Fungible units are interchangeable within one contract: any one unit has the same accounting role as another.

Core ERC-20 functions include:

```text
totalSupply()
balanceOf(owner)
transfer(to, amount)
approve(spender, amount)
allowance(owner, spender)
transferFrom(owner, to, amount)
```

`Transfer` and `Approval` events let wallets and indexers follow changes.

The token is identified by chain ID and contract address. Name and symbol are optional metadata and can be copied by unlimited fake contracts.

## Why the standard matters

Wallets, exchanges, DEX routers, lending protocols, and bridges can integrate one interface instead of custom logic for every fungible asset.

The standard defines observable behavior, not one implementation. Contracts may add minting, burning, pausing, fees, voting, rebasing, blacklisting, snapshots, or upgradeability.

## Compatibility is messy

Historical tokens do not all return values exactly as modern callers expect. Safe integration libraries handle tokens that return `false`, return no bytes, charge transfer fees, or change balances through rebases.

Never assume:

```text
requested transfer amount = recipient's balance increase
```

Fee-on-transfer and rebasing tokens can violate that assumption while still exposing familiar function names.

## Decimals are presentation

`decimals()` tells interfaces how to display integer units. A token with six decimals represents one displayed token as `1,000,000` base units.

The EVM performs integer arithmetic. Decimals do not add floating point and do not determine value.

## Standard does not mean safe

An ERC-20 can have an unlimited admin mint, blocked selling, upgradeable malicious logic, or no liquidity. Conformance only makes calls predictable enough to integrate.

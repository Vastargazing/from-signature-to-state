# ERC-1155

> **ERC-1155 lets one contract manage many token IDs, each with its own fungible or non-fungible supply, and transfer them in batches.**

## One contract, many asset types

An ERC-1155 balance is indexed by both token ID and owner:

```text
balance[id][owner]
```

ID `1` might represent one million identical gold units. ID `2` might have supply one and behave like a unique sword. The standard does not force every ID into one fungibility category.

This fits games, tickets, editions, and collections containing many item types.

## Batch operations

`safeBatchTransferFrom` moves several IDs and amounts in one call. Batch balance queries also reduce integration overhead.

Compared with deploying many ERC-20 contracts or making many ERC-721 calls, shared code and batching can save deployment, execution, and indexing cost.

## Safe receiver checks

Transfers to contracts require the appropriate ERC-1155 receiver callback. Batch and single transfers use distinct acceptance functions.

The callback improves safety but also creates an external call during transfer. Implementations must consider reentrancy and update state in a safe order.

## Operator approval

ERC-1155 uses `setApprovalForAll`. An approved operator can move all token IDs belonging to the owner within that ERC-1155 contract.

The base standard has no per-ID approval. Applications wanting narrower permissions need an additional mechanism.

## Events reconstruct supply and balances

`TransferSingle` and `TransferBatch` events cover transfers, minting, and burning. The standard is designed so indexers can reconstruct token activity from events when implementations follow it correctly.

Metadata often uses a URI template containing the token ID. As with ERC-721, external metadata may be mutable or unavailable even while on-chain balances remain valid.

# Ed25519

> **Ed25519 is a concrete signature scheme with deterministic signing and fixed-size keys and signatures.**

Ed25519 combines the EdDSA design, the Edwards25519 curve, SHA-512, and strict byte encodings. Public keys are 32 bytes and signatures are 64 bytes.

It is related to X25519 but does a different job. Ed25519 creates signatures; X25519 establishes shared secrets. Similar names and byte lengths do not make their keys interchangeable.

## Why deterministic signing matters

ECDSA fails catastrophically when its secret signing nonce repeats. Ed25519 derives its per-message nonce from secret key material and the message:

```text
secret material + message → deterministic nonce → signature
```

The same key signing the same bytes produces the same signature. Correctness no longer depends on generating fresh random nonce material for every signature.

This does not make every implementation safe. Weak key generation, key theft, timing leaks, fault attacks, and inconsistent point or scalar validation can still break a system. Use reviewed libraries whose verification behavior matches the protocol: Ed25519 verification variants do not all accept exactly the same encodings and edge cases.

## Where it appears

Normal Solana transactions use Ed25519 signatures. Public keys are 32 bytes, and their Base58 form commonly serves directly as the account address.

NEAR also commonly uses Ed25519 for account access keys, although its protocol supports typed keys and is not defined as “Ed25519 only.”

In both cases, the chain—not Ed25519 alone—decides which bytes are signed, how keys are tagged, and how signatures authorize state changes.

## Rust lens

Rust infrastructure often uses `ed25519-dalek`, while chain SDKs wrap it in protocol-specific types. Prefer those types over `[u8; 32]`: an Ed25519 public key, a seed, and an X25519 public key may have the same length but different meanings.

The engineering win is fewer dangerous choices, not automatic security.

# VRF and Verifiable Randomness

> **A verifiable random function produces a random-looking value plus a proof that a specific key generated it from a specific input.**

## Request and fulfillment

A consumer contract requests randomness and receives an identifier. An oracle later combines the request data with secret-key computation, then submits the output and cryptographic proof.

The coordinator verifies the proof on-chain before calling the consumer:

```text
request → wait for confirmations → output + proof → verified callback
```

The oracle cannot freely choose among outputs without failing verification. The contract does not need to trust an API response blindly.

## Why it is asynchronous

Randomness unknown at request time must come from a future event or private computation. A contract cannot both request and consume unpredictable VRF output synchronously in the same call.

Games therefore record the request, wait for fulfillment, and handle the result in a later transaction.

## What the proof does not solve

The oracle may delay or refuse fulfillment. A consumer must define timeout and retry behavior without allowing users to reroll an unfavorable result.

Blockchain reorganizations can also change the request's context. Waiting for enough confirmations makes it more expensive to rewrite the request block and obtain a different valid outcome.

Consumer code must bind every callback to the correct request and prevent duplicate settlement. Its callback also needs enough gas and should not revert permanently due to unrelated game logic.

## Fairness is the whole flow

A valid random number does not guarantee a fair game if an admin can change prizes afterward, users can choose whether to reveal, or the contract leaks the outcome before bets close.

VRF proves generation. Application state and timing determine how that value can be used.
